# 箭箭火模块复活 APNs 的尝试

??? quote "QUO"
    该项目含有**内部引用**，即本网站内其他项目的引用，如果修改文件结构，请注意对应引用链接是否需要变化。

## 更新

给出一[模块](https://raw.githubusercontent.com/eepsjo/s/refs/heads/m/apns)解决 [APNs 的问题](../../26/9.箭箭火 + 捷徑：按应用分流.md/#fn:4)。模块更新移除了一些不是很重要的参数，在下面的[原文](#_3)一章中你可以找到老版和相关的参数意义。

更新内容：

1. 废弃 `interval` & `tolerance` & `timeout` & `url`
2. *破坏性更新* 废弃 `mode`，现在模块的默认行为是 `fallback` 且默认回退到 `DIRECT`
3. *破坏性更新* `url-test` 键名改为 `node`，作为 `fallback` 的一部分。填写多个节点时用“,”隔开
4. `init-?01st.push.apple.com` 对应的规则从原来的 `DOMAIN-WILDCARD` 改为尊重 [D 规则集](https://raw.githubusercontent.com/Loyalsoldier/clash-rules/refs/heads/release/direct.txt)的两条 `DOMAIN`

简单来说现在**只保留了填写“用于接收 APNs 推送的节点”的参数**，以及开关后面三类规则的参数。

### 补充几句

笔者仍认为 APNs 问题是 Apple 的主动屏蔽（或者说被迫在东大“合规”）导致的，而 GFW 就算没有知道具体 APNs 推送的来源 APP 和信息内容的方法，其通过 DPI 等手段，甚至是直接与 Apple 沟通还是极有可能暴露我们使用海外 APP 的事实。

**最佳实践是：除非你有这些被屏蔽 APP 的即时消息接收需求，否则不要使用模块，且在设置中直接关闭这些 APP 的消息推送。**

此外不要为了消息及时接收去使用任何第三方 APP。

## 原文

给出一模块解决 APNs 的问题：

```ini
#!name=[e] apns
#!desc=APNs 代理 - 编辑参数
#!arguments=mode:"fallback",url-test:"PROXY",fallback:"DIRECT",interval:"600",tolerance:"66",timeout:"3",url:"http://www.gstatic.com/generate_204",init-?01st.push.apple.com:"false",+.push.apple.com:"true",IPs:"true"

[Proxy Group]
false = select,DIRECT
true = select,{{{mode}}}
url-test = url-test,{{{url-test}}},interval={{{interval}}},tolerance={{{tolerance}}},timeout={{{timeout}}},url={{{url}}}
fallback = fallback,url-test,{{{fallback}}},interval={{{interval}}},timeout={{{timeout}}},url={{{url}}}

[Rule]
DOMAIN-WILDCARD,init-?01st.push.apple.com,{{{init-?01st.push.apple.com}}}
DOMAIN-SUFFIX,push.apple.com,{{{+.push.apple.com}}}
IP-CIDR,17.249.0.0/16,{{{IPs}}},no-resolve
IP-CIDR,17.252.0.0/16,{{{IPs}}},no-resolve
IP-CIDR,17.57.144.0/22,{{{IPs}}},no-resolve
IP-CIDR,17.188.128.0/18,{{{IPs}}},no-resolve
IP-CIDR,17.188.20.0/23,{{{IPs}}},no-resolve
IP-CIDR,2620:149:a44::/48,{{{IPs}}},no-resolve
IP-CIDR,2403:300:a42::/48,{{{IPs}}},no-resolve
IP-CIDR,2403:300:a51::/48,{{{IPs}}},no-resolve
IP-CIDR,2a01:b740:a42::/48,{{{IPs}}},no-resolve
```

模块的工作原理和实现，基于笔者对 APNs 屏蔽的技术原理的*猜测*：*笔者认为，APNs 直接通过 APNs 连接检测用户的 IP 来确定用户是否在墙内，以此屏蔽指定应用的消息推送。*因此让 APNs 服务器认为我们在境外就能复活 APNs。

实测发现使用模块时的两个注意点。
  
1. 确保箭箭火隧道始终开启的情况下，使用[兜底代理配置](https://raw.githubusercontent.com/eepsjo/s/refs/heads/c/p)时默认 APNs 就是正常状态，不需要使用模块复活；

    > 兜底代理配置中没有规定 APNs 相关域名/IP 直连，[兜底直连配置](https://raw.githubusercontent.com/eepsjo/s/refs/heads/c/d)中也没有规定它们代理。模块本身不强制 APNs 代理，提供了丰富的可编辑参数（见下文），只是模块的默认行为同兜底代理的网络行为（至少在 APNs 相关内容上）。

2. 部分运营商使用 SIM 卡的蜂窝数据时，需要开启箭箭火的

    > $设置 \to 隧道 \to 包括所有网络 \to 包括 APNs$

    才能复活 APNs。Wi-Fi 不受影响（即不插卡的设备不需要）。

### mode & url-test & fallback

`mode` 可选值有 `url-test` 和 `fallback`，需要手动填写完整键值，代表模块将以哪种模式代理 APNs 流量。缺省值 `fallback`。

`url-test` 中可填入一个或多个代理节点或分组的名称，每个节点或分组之间用英文逗号分隔。这些节点将进行 URL 测试，测试结果最好的节点将被用来代理 APNs。不填则使用缺省值 `PROXY`。建议填写一个或多个稳定、低延迟的节点。

`fallback` 可填入一个或多个代理节点或分组的名称，每个节点或分组之间用英文逗号分隔。这些节点将在 `url-test` 中的节点都不可用时被使用。不填则使用缺省值 `DIRECT`，也建议使用缺省值。

> 手动指定固定的节点，目的是防止切换配置时/代理组切换节点时打断 APNs 长连接导致信息接收延迟。<br>直连作为回落兜底防止节点全部超时导致 APNs 完全失效（至少直连时不需要绕过 APNs 屏蔽的应用还能收到消息）。

### interval & tolerance & timeout & url

上述模式参数，一般不需要手动设置。具体用法参照[箭箭火使用文档](https://lowertop.github.io/Shadowrocket/)。

### init-?01st.push.apple.com

是否代理 `DOMAIN-WILDCARD,init-?01st.push.apple.com`。默认关闭（开启表示代理，关闭以切换到直连。下同）。

> 在兜底代理配置的 D 规则集中存在两条直连规则与下一条参数冲突，故创建此选项让用户自行定夺。

   ```yaml
   payload:
     - 'init-p01st.push.apple.com'
     - 'init-s01st.push.apple.com'
   ```

### +.push.apple.com

是否代理 `DOMAIN-SUFFIX,push.apple.com`。默认开启。

### IPs

是否代理 APNs 的 IP 段。默认开启。

参考了 [Apple 的官方文档](https://support.apple.com/102266)，这里说明了 APNs 的 IP 段。

按需配置完成后，可能需要编译一次正在使用的配置，和/或开关飞行模式一次（目的是彻底关闭再开启一次箭箭火隧道）。
